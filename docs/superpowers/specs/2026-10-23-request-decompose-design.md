# Request 分解列

日付: 2026-10-23  
対象: LogFormat に Request（引数なし `%r`）がある案件で、取り込み時にメソッド・パス・クエリ・プロトコルを別列として持つ。

承認済み。既存案件は変換しない。新規案件と今後の取り込みだけが対象。

## 1. 目的

`%r` の値（例: `GET /search?q=foo HTTP/1.1`）を、フィルタ・集計・CSV で個別に使える列へ分解する。元の Request 列は残す。

## 2. 対象

- 条件: LogFormat に引数なしの `%r` がある（フィールド識別子 `Request`）。
- 対象外: `%{名前}r`、ヘッダー名が `Request` の列、既存案件の自動変換。
- 既存案件で使うには、案件を作り直して再取り込みする。

## 3. 追加する列

案件登録時（LogFormat 解析）に、`Request` の直後へ次を挿入する。型はすべて文字列。指定子は合成値 `derived:%r`（LogFormat 上の指定子ではない）。

| フィールド識別子 | 内容 |
| ---------------- | ---- |
| Request-Method | Request のメソッド |
| Request-Path | パス。最初の `?` 以降を含まない |
| Request-Query | クエリ。先頭の `?` は付けない |
| Request-Protocol | プロトコル（`HTTP/1.1` など） |

`Request` より後の LogFormat 列は、この 4 列の分だけ表示順をずらす。

識別子が LogFormat 側の列と重なるときは、既存どおり E_CSE_DUP01 で案件を作れない。

## 4. 分解規則

行マッチ用パターンの捕捉グループは、LogFormat 由来の列だけとする。分解列は捕捉に含めない。行が解釈できて Request の値が取れたあと、その文字列から 4 列を足す。

例:

| Request | Method | Path | Query | Protocol |
| ------- | ------ | ---- | ----- | -------- |
| `GET /search?q=foo&p=1 HTTP/1.1` | `GET` | `/search` | `q=foo&p=1` | `HTTP/1.1` |
| `GET /index HTTP/1.1` | `GET` | `/index` | 空文字（未設定ではない） | `HTTP/1.1` |
| `GET /index` | `GET` | `/index` | 空文字 | 未設定 |
| `-` | 未設定 | 未設定 | 未設定 | 未設定 |

手順:

1. Request が `-` なら 4 列とも未設定。
2. 先頭のトークンを Method とする。取れなければ Method は未設定。
3. 末尾のトークンが `HTTP/` で始まるなら Protocol とし、残りをリクエストターゲットとする。該当が無ければ Protocol は未設定、残り全体をリクエストターゲットとする。
4. リクエストターゲットを最初の `?` で分ける。前が Path、後が Query（`?` は含めない）。`?` が無ければ Path はターゲット全体、Query は空文字。
5. 途中の断片が取れない属性だけ未設定にする。行は破棄しない。

絶対 URI（`GET http://host/foo?x=1 HTTP/1.1`）の Path は `http://host/foo` とする。URL としての再解釈はしない。

## 5. 画面と周辺

分解列は通常のログ列と同じ経路で扱う。

- 一覧、フィルタ、集計のグループ、一致行 CSV、スキーマ
- カスタムフィールド名との重複禁止も、既存のログ識別子規則のまま

取り込み失敗（行破棄）の条件は変えない。分解不能は破棄理由にしない。

## 6. テスト

- `%r` ありの LogFormat で 4 列が Request 直後に定義される
- `%r` なしでは 4 列が無い
- 上表の分解例
- Request が `-` のとき 4 列が未設定
- 識別子衝突で案件登録が失敗する
- 既存の `%r` 行マッチ・重複判定・破棄は回帰しない
