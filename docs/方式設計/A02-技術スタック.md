## 3. 方式方針

CPython 上の Flask で HTML を返す。DB アクセスは標準の sqlite3。圧縮ログは標準 gzip。LogFormat 解釈は自前とする（方式: 外部パーサ製品に依存しない）。

## 5. 選定比較

| 候補 | 概要 | 利点 | 欠点 | 費用（構築／運用） | 結果 |
|------|------|------|------|-------------------|------|
| Python | 言語 | ログ解釈と HTML が速い。ライセンス費用なし | 実行にランタイムが要る | 構築小／Python 導入が初回のみ | 採用 |
| Go | 単一バイナリ | ランタイム不要 | 画面とパーサの記述量増 | 初回構築中／配置は安い | 却下 |
| Node.js | TypeScript | 動的 UI に強い | SSR 方針だとビルドが過剰 | 構築中／Node 導入 | 却下 |
| Flask | 軽量 SSR | 依存が小さい | 大規模機能は自前 | 構築小／運用料金なし | 採用 |
| Django | フルスタック | 管理画面が付く | 一人用に厚い | 構築大／設定の運用 | 却下 |
| 標準 HTTP のみ | 枠なし | 依存ゼロ | ルーティング等を自作 | 工数が実増／運用は軽い | 却下 |

### 採用理由

取り込みと HTML 返却が中心なので、Python + Flask が構築費最小。Go の単一バイナリは運用は楽だが初回工数が増える。

### 却下理由

Django は管理画面が今回の簡易 UI と重複する。Node は SSR 方針と費用が合わない。標準 HTTP のみは自作コストが大きい。

## 6. 非機能への寄与

| 区分 | 本方式での対応 | 指標との関係 |
|------|----------------|--------------|
| 性能 | CPython と SQLite。落ちないことが目標 | 秒数上限なし |
| 運用性 | 依存が Flask 程度 | 更新対象が少ない |
| その他 | 有償ライセンスなし | 費用抑制 |

## 7. 運用・移行上の留意点

- Python のバージョンを大きく変えるときは動作確認する（手順は書かない）
- Flask の開発サーバを本番相当として使う。別途 gunicorn 等は置かない（Windows・一人・都度）

| 項目 | 内容 | 基本設計での扱い |
